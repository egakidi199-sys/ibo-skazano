## Context

Проект создаётся с нуля. Прообраз архитектуры — `C:\Claude\AstroStrikeBack`: Vite + React + TS + Tailwind, Cloudflare Pages Function как прокси к LLM, `functions/lib/llm.ts` с переключением провайдера через `LLM_PROVIDER` (в проде Groq `openai/gpt-oss-120b`), Zod-валидация, рейт-лимит в KV с fail-open, общий код в `src/shared/` с относительными импортами, открытка через `html-to-image` с self-hosted woff2, ручной деплой через `wrangler`. Из Astro переносим не только стек, но и уже выученные уроки: `wrangler login` в этой среде не работает (нужен `CLOUDFLARE_API_TOKEN`), секреты задаются через `printf | wrangler pages secret put` в Bash, TypeScript закреплён на 6.x из-за `typescript-eslint`.

Главное отличие от Astro: вместо свободной генерации текста — выбор из закрытого корпуса примерно из 27 тысяч стихов. Отсюда ограничения:
- **Лимит CPU Workers на бесплатном тарифе — около 10 мс на запрос.** Разобрать весь корпус (несколько МБ JSON) на сервере в рамках одного запроса нельзя, а время ожидания ответа LLM в этот лимит не входит.
- **Нумерация.** LLM обучены в основном на западной нумерации (KJV). Синодальная нумерация расходится с ней в Псалтири (для большинства псалмов номер на 1 меньше, а надписания считаются стихом 1) и в нескольких местах других книг (например, Мал 4 = Мал 3:19–24 в западных изданиях, есть сдвиги в Иов, Песн, Дан). Модель будет ошибаться в номерах — это ожидаемо, а не исключение.

## Goals / Non-Goals

**Goals:**
- Инвариант «текст цитаты только из корпуса» обеспечивается архитектурой (LLM физически не передаёт текст в UI), а не промптом.
- Серверная функция укладывается в лимит CPU: на запрос загружаются только книги, на которые есть ссылки.
- Одна реализация подбора без LLM, работающая и на сервере, и в браузере.
- Модули `src/shared/` покрыты юнит-тестами (Vitest). В Astro тестов не было, здесь корректность ссылок критична.

**Non-Goals:**
- Семантический поиск на эмбеддингах и векторная БД.
- Поиск по всему корпусу на сервере.
- Service worker и полноценный офлайн-режим PWA: браузерный подбор без сервера работает, пока открыта страница и доступны статические файлы.

## Decisions

### D1. Корпус — статические JSON-файлы по книгам, метаданные — в коде
- `scripts/build-corpus.mjs` один раз конвертирует исходный файл в `public/corpus/<id>.json` (по файлу на книгу: `{ id, chapters: string[][] }`) и генерирует `src/shared/corpus/books.ts`: id, каноническое сокращение, полное название, алиасы для разбора и **число стихов в каждой главе**.
- Благодаря `books.ts` проверка существования ссылки (главы и стиха) работает синхронно, без загрузки текста. Текст загружается только для показа и проверки ключевых слов.
- Сервер читает книги через `env.ASSETS.fetch()` из статических файлов того же деплоя. Клиент читает их через `fetch('/corpus/<id>.json')` с кешированием в памяти.
- **Альтернативы:** бандлить корпус в функцию (упрёмся в лимит размера и CPU на разбор), держать в KV (лишние операции чтения при бесплатном лимите, отдельный шаг загрузки), D1 с FTS (избыточно для MVP, отдельная инфраструктура).

### D2. Источник текста
- Основной кандидат — открытый JSON Синодального перевода (например, `ru_synodal.json` из репозитория `thiagobodruk/bible` или аналог). Синодальный перевод 1876 года находится в общественном достоянии, но нужно проверить лицензию самого файла и нумерацию.
- Скрипт сборки **обязан** проверять эталоны: число книг 39 + 4; число стихов в выборочных главах совпадает с синодальным; `Пс 22:1` содержит «Пастырь»; `Пс 50` — покаянный псалом («Помилуй меня, Боже»); `Мал` имеет 4 главы; `Ин 3:16` содержит «Ибо так возлюбил Бог мир». Если источник даёт западную нумерацию, его отбрасываем и берём другой, а не перенумеровываем вручную.

### D3. Ссылки и их разбор — чистый модуль `src/shared/reference.ts`
- Тип `Ref = { book, chapter, verseFrom, verseTo }`, функции `parseRef(string)`, `formatRef(Ref)`, `validateRef(Ref)` (возвращает причину отказа: книга вне корпуса, нет главы, нет стиха, длинный диапазон).
- Алиасы книг включают частые формы от LLM: «Матфей», «От Матфея», «Мат», «Psalm»/«Ps» не нужны — модель просим отвечать русскими сокращениями, а неразобранное отбрасываем.
- Отдельный список книг вне корпуса («Рим», «Деян», «Откр», «Сир», «Прем», «Тов» и т. д.), чтобы причина отказа была «вне корпуса», а не «не распознано». Это нужно для отладки промпта.

### D4. Контракт LLM: только ссылки, ключевые слова, направленность, пояснение
- Плоская JSON-схема по образцу Astro (провайдеры непоследовательно поддерживают oneOf):
  `{ refusal: "none"|"harm"|"crisis", thesis: string, no_direct_support: boolean, candidates: [{ ref: string, keywords: string[], stance: "confirm"|"refute", explanation: string }] }`, до 6 кандидатов.
- **В схеме нет поля для текста стиха.** Даже если модель вставит текст в `explanation`, UI показывает текст только из корпуса. Пояснение режется до 300 символов и проходит проверку «не содержит кавычек-цитаты длиннее N слов». Такое пояснение не отбрасывается, а заменяется шаблонным.
- Промпт (`functions/lib/prompts.ts`) содержит: роль (внимательный знаток Писания, нейтральный тон), состав корпуса с явным списком допустимых книг, требование синодальной нумерации с примерами расхождений (Пс 22 вместо Ps 23, Пс 50 вместо Ps 51), правило честности (`no_direct_support`), правила отказа, указание воспринимать текст пользователя как данные внутри разделителей и few-shot для трёх позиций.
- Список `exclude` (ссылки, уже показанные при «Ещё вариант», до 30 штук) передаётся модели и дополнительно отфильтровывается на сервере.

### D5. Конвейер проверки кандидата (сервер, `functions/lib/verify.ts` поверх `src/shared/`)
1. `parseRef` → `validateRef`: неразобранное, вне корпуса и несуществующее отбрасывается.
2. Загрузка нужных книг (параллельно, только уникальные).
3. Проверка ключевых слов: основы из `keywords` сравниваются с основами слов стиха (русский стеммер Портера из `src/shared/stem.ts`). Ноль совпадений — кандидат считается сдвинутым.
4. **Попытка спасти сдвинутую ссылку:** для Псалтири проверяются псалом n−1 (западная → синодальная нумерация) и стихи ±2 в псалмах n и n−1; для остальных книг — стихи ±2 в той же главе. Берётся вариант с максимальным совпадением ключевых слов, если совпадений ≥ 2 (или все, если ключевых слов меньше 2). Иначе кандидат отбрасывается.
5. Дедупликация (пересекающиеся диапазоны), фильтр `exclude`, отбор: главная + до 2 запасных; для `both` гарантируется наличие обеих направленностей, если они есть среди прошедших проверку.
6. Если никто не прошёл проверку — `fallback-search` (темы на сервере; см. D6).
- **Альтернатива:** сначала поиск кандидатов по корпусу, потом выбор LLM (RAG). Отклонена пользователем в пользу проверки после выбора: проще, и не требует поиска по корпусу на сервере.

### D6. Fallback: одна реализация в `src/shared/fallback.ts`, два режима доступа к корпусу
- `fallbackSelect(query, stance, exclude, corpus: CorpusReader)`, где `CorpusReader` — интерфейс `getBook(id)` с серверной реализацией (ASSETS) и клиентской (fetch + кеш).
- Шаг 1 — тематический указатель `src/shared/themes.ts`: не менее 40 тем, для каждой основы-триггеры и ссылки со `stance` относительно «основного тезиса темы». Направленность для запроса выводится так: `confirm`-стихи темы подходят позиции `confirm`, если тезис пользователя не содержит отрицания основного тезиса темы. Детектор отрицания простой — «не», «нельзя», «незачем» рядом с триггером. При сомнении цитаты помечаются «По теме». Работает и на сервере: загружаются только книги найденных тем.
- Шаг 2 — поиск по ключевым словам по **всему корпусу**. Выполняется **только в браузере** (загрузка всех книг ≈ 1–1,5 МБ gzip — приемлемо для браузера, недопустимо для CPU Worker). Сервер при пустом результате по темам отвечает `{ source: "fallback", quotes: [], needsClientSearch: true }`, и клиент выполняет шаг 2 сам.
- Отдельная функция не нужна: когда сервер недоступен, клиент вызывает тот же `fallbackSelect` с клиентским `CorpusReader`.

### D7. Отказы
- Решение об отказе принимает модель (`refusal`). Дополнительно в `src/shared/safety.ts` есть небольшой эвристический бэкстоп: словарь основ для явного насилия над людьми и суицидальных формулировок. В Astro бэкстопа не было, и модель пропускала случаи; здесь цена ошибки выше — цитата «в подтверждение» насилия.
- Бэкстоп работает и в fallback (где модели нет): при срабатывании fallback не подбирает цитаты и возвращает отказ. `crisis` показывает сообщение с номером 112.

### D8. Таймауты
- Общий бюджет сервера — 9 с. Первый вызов LLM — таймаут 6 с; повтор только при невалидном JSON и только если осталось больше 3 с. Клиентский таймаут запроса — 10 с, после чего клиент переходит на свой fallback.
- Для Gemini `thinkingBudget: 0` (как в Astro). Для `gpt-oss` в Groq — `reasoning_effort: "low"`: выбор ссылок выигрывает от небольшого рассуждения, но латентность важнее.

### D9. Рейт-лимит и хранение
Перенос `rateLimit.ts` из Astro без изменений логики: фиксированное окно, ключ `rl:{ip}:{hourBucket}`, TTL 3600, fail-open без привязки KV. Лимит бесплатного KV (1000 записей в сутки) покрывает целевые 500 запросов в сутки. Тексты запросов не логируются: `console.log` в функции — только коды ошибок и тип источника.

### D10. Фронтенд
- Одна основная страница `/` и страница `/about` (`react-router-dom`, `_redirects` для SPA, как в Astro).
- Визуальный стиль — спокойная «книжная» эстетика: светлая тема «пергамент» по умолчанию и тёмная по `prefers-color-scheme`. Текст стихов набран антиквой с кириллицей (self-hosted woff2), интерфейс — гротеском. Иконки `lucide-react`.
- Открытка: подход Astro (узел вне экрана, инлайновые стили, `pixelRatio: 4` → 1080×1350). Размер шрифта подбирается по длине текста из 3 ступеней.
- Позиция и уже показанные ссылки для «Ещё вариант» хранятся в `localStorage` и памяти соответственно, с try/catch.

### D11. Тесты
Vitest для `src/shared/`: разбор и форматирование ссылок, проверка существования по `books.ts`, стеммер на наборе словоформ, конвейер проверки кандидатов на заготовленных ответах LLM (в том числе со сдвигом Псалтири), целостность тематического указателя (все ссылки действительны, у каждой темы ≥ 4 ссылки), fallback на примерах из спецификаций. Серверная функция — ручной smoke через `wrangler pages dev`.

## Risks / Trade-offs

- [Модель систематически ссылается не на тот стих] → проверка ключевыми словами + спасение соседних стихов (D5), при провале — fallback. В приёмке: прогон 30 эталонных ситуаций, доля ответов с хотя бы одной проверенной цитатой от LLM ≥ 80%.
- [Ключевые слова тоже выдуманы моделью и случайно совпадают с неверным стихом] → порог ≥ 2 совпадений для спасённых ссылок. Для исходной ссылки хватает одного совпадения — это компромисс: частые слова («Господь», «сказал») исключаются стоп-списком.
- [Цитата верна текстуально, но вырвана из контекста] → кнопка «Показать контекст», оговорка на странице «О приложении», в промпте запрет на стихи, где слова принадлежат отрицательному персонажу (например, речи друзей Иова, слова змея), без явного указания на это в пояснении.
- [Модель пропускает оправдание вреда] → эвристический бэкстоп (D7). Ложные срабатывания допустимы: пользователь переформулирует.
- [Размер корпуса для клиентского поиска по ключевым словам] → загрузка только при шаге 2 fallback, gzip/brotli от Cloudflare, кеш браузера. Основной путь (LLM) грузит 1–3 книги.
- [Лицензия и качество исходного JSON] → проверки эталонов в скрипте сборки (D2). Источник фиксируется в README и на странице «О приложении».
- [Бесплатные лимиты Groq меняются] → переключение провайдера через `LLM_PROVIDER` без правки кода, как в Astro.

## Migration Plan

Новый проект, миграций нет. Деплой: создать GitHub-репозиторий `ibo-skazano` и Cloudflare Pages проект `ibo-skazano` с KV `RATE_LIMIT_KV`, задать секреты, выполнить `npm run build && wrangler pages deploy dist`. Откат — повторный деплой предыдущей сборки или переключение на прошлый деплой в панели Cloudflare. `git push` и первая публикация — только после подтверждения пользователя.

## Open Questions

- Какой именно JSON-источник Синодального перевода пройдёт проверки из D2. Выбор не меняет архитектуру: скрипт сборки конвертирует любой формат в свой.
- Точный набор и формулировки 40+ тем указателя — составляются при реализации и проверяются тестом целостности.
