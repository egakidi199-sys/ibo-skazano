## Context

Проект создаётся с нуля. Прообраз архитектуры — `C:\Claude\AstroStrikeBack`: Vite + React + TS + Tailwind, Cloudflare Pages Function как прокси к LLM, `functions/lib/llm.ts` с переключением провайдера через `LLM_PROVIDER` (в проде Groq `openai/gpt-oss-120b`), Zod-валидация, рейт-лимит в KV с fail-open, общий код в `src/shared/` с относительными импортами, открытка через `html-to-image` с self-hosted woff2, ручной деплой через `wrangler`. Из Astro переносим не только стек, но и уже выученные уроки: `wrangler login` в этой среде не работает (нужен `CLOUDFLARE_API_TOKEN`), секреты задаются через `printf | wrangler pages secret put` в Bash, TypeScript закреплён на 6.x из-за `typescript-eslint`.

Главное отличие от Astro: вместо свободной генерации текста — выбор из закрытого корпуса примерно из 27 тысяч стихов. Отсюда ограничения:
- **Лимит CPU Workers на бесплатном тарифе — около 10 мс на запрос.** Разобрать весь корпус (несколько МБ JSON) на сервере в рамках одного запроса нельзя, а время ожидания ответа LLM в этот лимит не входит.
- **Нумерация.** LLM обучены в основном на западной нумерации (KJV). Синодальная нумерация расходится с ней в Псалтири (для большинства псалмов номер на 1 меньше, а надписания считаются стихом 1) и в нескольких местах других книг (например, Мал 4 = Мал 3:19–24 в западных изданиях, есть сдвиги в Иов, Песн, Дан). Модель будет ошибаться в номерах — это ожидаемо, а не исключение.

## Goals / Non-Goals

**Goals:**
- Инвариант «текст цитаты только из корпуса» обеспечивается архитектурой (LLM физически не передаёт текст в UI), а не промптом.
- Серверная функция укладывается в лимит CPU: на запрос загружаются только книги, на которые есть ссылки.
- Одна реализация подбора без LLM, работающая и на сервере, и в браузере.
- Модули `src/shared/` покрыты юнит-тестами (Vitest). В Astro тестов не было, здесь корректность ссылок критична.

**Non-Goals:**
- Семантический поиск на эмбеддингах и векторная БД.
- Поиск по всему корпусу на сервере.
- Service worker и полноценный офлайн-режим PWA: браузерный подбор без сервера работает, пока открыта страница и доступны статические файлы.

## Decisions

### D1. Корпус — статические JSON-файлы по книгам, метаданные — в коде
- `scripts/build-corpus.mjs` один раз конвертирует исходные файлы в `public/corpus/<id>.json` (по файлу на книгу: `{ id, chapters: string[][], headings?: Record<chapter, string> }`, где `headings` — нецитируемые надписания, «стих 0» источника) и генерирует `src/shared/corpus/books.ts`: id, каноническое сокращение, полное название, алиасы для разбора и **число стихов в каждой главе**.
- Благодаря `books.ts` проверка существования ссылки (главы и стиха) работает синхронно, без загрузки текста. Текст загружается только для показа и проверки ключевых слов.
- Сервер читает книги через `env.ASSETS.fetch()` из статических файлов того же деплоя. Клиент читает их через `fetch('/corpus/<id>.json')` с кешированием в памяти.
- **Альтернативы:** бандлить корпус в функцию (упрёмся в лимит размера и CPU на разбор), держать в KV (лишние операции чтения при бесплатном лимите, отдельный шаг загрузки), D1 с FTS (избыточно для MVP, отдельная инфраструктура).

### D2. Источник текста
- **Выбрано:** [bibleonline/rst](https://github.com/bibleonline/rst), каталог `parsed/` (полное издание из 77 книг). Используем только 39 книг ВЗ и 4 Евангелия. Источник закреплён на коммите `2de3062388a2c067bc602399bda7149eec918ceb` (2026-04-11). Исходные файлы копируются в `data/rst/` и коммитятся: сборка не зависит от сети, а обновление источника делается осознанно.
- **Почему он:** это исходник bible.ru, взятый из Logos (РБО, 1995, Public Domain) и вычитанный по печатным изданиям РБО 2002 и МП РПЦ 2016; ошибки набора разобраны в `issues/`, репозиторий поддерживается. Нумерация синодальная: Пс 22:1 — «Господь — Пастырь мой», Пс 50:3 — «Помилуй меня, Боже», Дан 3:24–90 — песнь трёх отроков, Дан 3:91 — «Навуходоносор царь… изумился». Типографика книжная: длинные тире, знаки ударения.
- **Отклонённые кандидаты** (проверены 2026-09-26):
  - `thiagobodruk/bible` `ru_synod.json` — нет книг Есфирь и Даниил.
  - eBible `russyn` (Public Domain) — у Даниила еврейская нумерация (Дан 3:24 = «Навуходоносор…», песни трёх отроков нет), дефис вместо тире.
  - `bibleonline/rst` `parsed66/` (протестантское издание) — после удаления квадратных скобок сломана нумерация: в Дан 3 стих 24 встречается дважды.
- **Лицензия:** текст Синодального перевода в общественном достоянии, у репозитория нет файла LICENSE. Источник указывается в README и на странице «О приложении».
- **Особенности формата** `#глава:стих#текст`, которые учитывает скрипт сборки:
  - Строки с одинаковым номером — один стих, разбитый на абзацы: склеиваются через пробел.
  - `#p#` — разрыв абзаца, отбрасывается.
  - «Стих 0» — надписание (короткие надписания псалмов, вступление Есфири): попадает в `headings`, не цитируется и не входит в счёт стихов. Длинные надписания псалмов в Синодальном издании — нумерованные стихи (Пс 50:1–2), они остаются стихами.
  - `&mdash;` → «—», `&nbsp;` → неразрывный пробел, `&#769;` → комбинируемый знак ударения U+0301 (при поиске и проверке ключевых слов удаляется); теги `<i>` (слова, добавленные переводчиками) снимаются.
  - Квадратные скобки (вставки по греческому тексту, как в синодальном издании МП РПЦ) сохраняются как есть.
  - Псалом 151 исключается: он неканонический («вне числа», в синодальном издании целиком в скобках). В корпусе 150 псалмов.
- Скрипт сборки **обязан** проверять эталоны и завершаться ошибкой при расхождении: 43 книги; нет повторяющихся номеров стихов после склейки; нет оставшихся HTML-сущностей и тегов; `Пс 22:1` содержит «Пастырь»; `Пс 50:3` содержит «Помилуй меня, Боже»; `Дан 3:91` содержит «Навуходоносор»; в `Мал` 4 главы; `Ин 3:16` содержит «Ибо так возлюбил Бог мир»; `Мф 5:9` содержит «Блаженны миротворцы».

### D3. Ссылки и их разбор — чистый модуль `src/shared/reference.ts`
- Тип `Ref = { book, chapter, verseFrom, verseTo }`, функции `parseRef(string)`, `formatRef(Ref)`, `validateRef(Ref)` (возвращает причину отказа: книга вне корпуса, нет главы, нет стиха, длинный диапазон).
- Алиасы книг включают частые формы от LLM: «Матфей», «От Матфея», «Мат», «Psalm»/«Ps» не нужны — модель просим отвечать русскими сокращениями, а неразобранное отбрасываем.
- Отдельный список книг вне корпуса («Рим», «Деян», «Откр», «Сир», «Прем», «Тов» и т. д.), чтобы причина отказа была «вне корпуса», а не «не распознано». Это нужно для отладки промпта.

### D4. Контракт LLM: только ссылки, ключевые слова, направленность, пояснение
- Плоская JSON-схема по образцу Astro (провайдеры непоследовательно поддерживают oneOf):
  `{ sensitive: boolean, thesis: string, no_direct_support: boolean, candidates: [{ ref: string, keywords: string[], stance: "confirm"|"refute", explanation: string }] }`, до 6 кандидатов.
- **В схеме нет поля для текста стиха.** Даже если модель вставит текст в `explanation`, UI показывает текст только из корпуса. Пояснение режется до 300 символов и проходит проверку «не содержит кавычек-цитаты длиннее N слов». Такое пояснение не отбрасывается, а заменяется шаблонным.
- Промпт (`functions/lib/prompts.ts`) содержит: роль (внимательный знаток Писания, нейтральный тон), состав корпуса с явным списком допустимых книг, требование синодальной нумерации с примерами расхождений (Пс 22 вместо Ps 23, Пс 50 вместо Ps 51), правило честности (`no_direct_support`), запрет отказов и признак `sensitive` для тезисов об оправдании вреда, указание воспринимать текст пользователя как данные внутри разделителей и few-shot для трёх позиций.
- Список `exclude` (ссылки, уже показанные при «Ещё вариант», до 30 штук) передаётся модели и дополнительно отфильтровывается на сервере.

### D5. Конвейер проверки кандидата (сервер, `functions/lib/verify.ts` поверх `src/shared/`)
1. `parseRef` → `validateRef`: неразобранное, вне корпуса и несуществующее отбрасывается.
2. Загрузка нужных книг (параллельно, только уникальные).
3. Проверка ключевых слов: основы из `keywords` сравниваются с основами слов стиха (русский стеммер Snowball из `src/shared/stem.ts`). Частые основы корпуса (встречаются более чем в 400 стихах: «сын», «земля», «дом»; список `src/shared/corpus/frequent.ts` генерирует сборка корпуса) не учитываются.
4. **Сдвинутые ссылки.** Синодальные номера не меньше западных (вставки по греческому тексту в Притчах, надписания псалмов), поэтому сдвиг ищется только вперёд: +1..+2 стиха; в Псалтири дополнительно псалом n−1 со сдвигом 0..+2. Порядок решений: исходная ссылка с ≥ 2 совпадениями (или все, если слово одно) принимается; иначе сдвинутая с ≥ 2 и строго большим числом совпадений; иначе для Псалтири — псалом n−1 (сдвиг 0..+1) хотя бы с одним совпадением, если у исходной ноль; иначе исходная с одним совпадением; иначе кандидат отбрасывается. Правило подобрано на живом прогоне: симметричный поиск ±2 «спасал» верные ссылки на случайных соседей (Притч 23:20–21 → 23:18–19).
5. Дедупликация (пересекающиеся диапазоны), фильтр `exclude`, отбор: главная + до 2 запасных; для `both` гарантируется наличие обеих направленностей, если они есть среди прошедших проверку.
6. Если никто не прошёл проверку — `fallback-search` (темы на сервере; см. D6).
- **Альтернатива:** сначала поиск кандидатов по корпусу, потом выбор LLM (RAG). Отклонена пользователем в пользу проверки после выбора: проще, и не требует поиска по корпусу на сервере.

### D5a. Второй проход по точному тексту (решение пользователя после эталонного прогона)
- Эталонный прогон (задача 7.2) показал: при одном проходе ~20% цитат имеют неверную направленность или пояснение не про этот стих, а правка промпта не помогла. Причина — модель пишет пояснение и ставит пометку по памяти, не видя текста. Худший случай — «подгонка» смысла под современные взгляды (Притч 13:25 «Кто жалеет розги своей…» помечен как опровергающий тезис о наказании).
- После сверки (D5) все прошедшие кандидаты вместе с **точным текстом из корпуса** отправляются второму вызову LLM (`functions/lib/ground.ts`, `GROUND_SYSTEM_PROMPT`). Для каждого стиха модель возвращает `relevant`, `explanation`, `stance`; нерелевантные отбрасываются, пометка и пояснение заменяются. Текст цитат не меняется — инвариант сохраняется.
- Промпт второго прохода явно требует честности: определять направленность по буквальному смыслу, не смягчать жёсткие стихи.
- Второй проход запускается, если в бюджете 9 с осталось ≥ 1,5 с; таймаут до 4 с. При сбое или таймауте остаётся результат первого прохода. Если все стихи признаны нерелевантными — упрощённый подбор.
- Цена: +1–2 с к ответу и ~+1,2 тыс. токенов на запрос (итого ~3,8 тыс.), то есть на бесплатном тарифе Groq ~50–55 ответов ИИ в сутки вместо ~80.
- **Альтернативы:** больше рассуждения в одном проходе (модель всё равно не видит текст); оставить как есть с оговоркой — отклонены пользователем.
- Устойчивость к сбоям схемы: кандидаты и оценки проверяются по одному (`lenientArray`), неверный элемент выбрасывается, а не роняет ответ. Режим `strict` у Groq не используется: с ним любой сбой генерации превращается в HTTP 400. Ошибка провайдера «Failed to generate JSON» повторяется один раз. На тезисе «Жену можно бить» gpt-oss стабильно срывается в такую ошибку (вероятно, встроенный отказ модели) — пользователь получает упрощённый подбор с обеими сторонами и пометкой sensitive.

### D6. Fallback: одна реализация в `src/shared/fallback.ts`, два режима доступа к корпусу
- `fallbackSelect(query, stance, exclude, corpus: CorpusReader)`, где `CorpusReader` — интерфейс `getBook(id)` с серверной реализацией (ASSETS) и клиентской (fetch + кеш).
- Шаг 1 — тематический указатель `src/shared/themes.ts`: не менее 40 тем, для каждой основы-триггеры и ссылки со `stance` относительно «основного тезиса темы». Направленность для запроса выводится так: `confirm`-стихи темы подходят позиции `confirm`, если тезис пользователя не содержит отрицания основного тезиса темы. Детектор отрицания простой — «не», «нельзя», «незачем» рядом с триггером. При сомнении цитаты помечаются «По теме». Работает и на сервере: загружаются только книги найденных тем.
- Шаг 2 — поиск по ключевым словам по **всему корпусу**. Выполняется **только в браузере** (загрузка всех книг ≈ 1–1,5 МБ gzip — приемлемо для браузера, недопустимо для CPU Worker). Сервер при пустом результате по темам отвечает `{ source: "fallback", quotes: [], needsClientSearch: true }`, и клиент выполняет шаг 2 сам.
- Отдельная функция не нужна: когда сервер недоступен, клиент вызывает тот же `fallbackSelect` с клиентским `CorpusReader`.

### D7. Без отказов; противовес для тезисов об оправдании вреда
- **Решение пользователя:** приложение не цензурирует Писание и не отказывает в подборе ни по какой теме, в том числе при тяжёлых личных ситуациях; особой «кризисной» обработки нет.
- Тезис, оправдывающий насилие над другими, помечается как чувствительный (`sensitive`). Признак ставит модель (поле `sensitive`) или эвристика `isHarmJustification` из `src/shared/safety.ts` — достаточно одного из двух. Эвристика работает и в fallback, где модели нет.
- Для чувствительного ответа отбор принудительно идёт по правилу `both` (обе стороны, если они есть), ответ несёт `sensitive: true`, UI сразу раскрывает контекст и показывает оговорку. Цитаты, подтверждающие тезис, не скрываются.
- **Альтернативы:** отказ (первая версия плана) скрывал бы существующий текст Писания и противоречил подбору без ИИ, где Притч 13:25 и так подтверждает «строгое наказание»; отключение открытки для таких тезисов — отклонено пользователем в пользу противовеса.

### D8. Таймауты
- Общий бюджет сервера — 9 с. Первый вызов LLM — таймаут 6 с; повтор только при невалидном JSON и только если осталось больше 3 с. Клиентский таймаут запроса — 10 с, после чего клиент переходит на свой fallback.
- Для Gemini `thinkingBudget: 0` (как в Astro). Для `gpt-oss` в Groq — `reasoning_effort: "low"`: выбор ссылок выигрывает от небольшого рассуждения, но латентность важнее.

### D9. Рейт-лимит и хранение
Перенос `rateLimit.ts` из Astro без изменений логики: фиксированное окно, ключ `rl:{ip}:{hourBucket}`, TTL 3600, fail-open без привязки KV. Лимит бесплатного KV (1000 записей в сутки) покрывает целевые 500 запросов в сутки. Тексты запросов не логируются: `console.log` в функции — только коды ошибок и тип источника.

### D10. Фронтенд
- Одна основная страница `/` и страница `/about` (`react-router-dom`, `_redirects` для SPA, как в Astro).
- Визуальный стиль — спокойная «книжная» эстетика: светлая тема «пергамент» по умолчанию и тёмная по `prefers-color-scheme`. Стихи — PT Serif (ParaType, спроектирован для кириллицы), интерфейс — Manrope; оба self-hosted через пакеты `@fontsource`. Иконки `lucide-react`. Нейтральный орнамент на открытке, без конфессиональных символов.
- Открытка: подход Astro (узел вне экрана, инлайновые стили, `pixelRatio: 4` → 1080×1350). Размер шрифта подбирается автоматически (уменьшается, пока текст не поместится, от 19 до 4 CSS-px): самая длинная допустимая цитата — Есф 4:13–17, около 4000 знаков.
- Позиция и уже показанные ссылки для «Ещё вариант» хранятся в `localStorage` и памяти соответственно, с try/catch.

### D11. Тесты
Vitest для `src/shared/`: разбор и форматирование ссылок, проверка существования по `books.ts`, стеммер на наборе словоформ, конвейер проверки кандидатов на заготовленных ответах LLM (в том числе со сдвигом Псалтири), целостность тематического указателя (все ссылки действительны, у каждой темы ≥ 4 ссылки), fallback на примерах из спецификаций. Серверная функция — ручной smoke через `wrangler pages dev`.

## Risks / Trade-offs

- [Модель систематически ссылается не на тот стих] → проверка ключевыми словами + спасение соседних стихов (D5), при провале — fallback. В приёмке: прогон 30 эталонных ситуаций, доля ответов с хотя бы одной проверенной цитатой от LLM ≥ 80%.
- [Ключевые слова тоже выдуманы моделью и случайно совпадают с неверным стихом] → порог ≥ 2 совпадений для спасённых ссылок. Для исходной ссылки хватает одного совпадения — это компромисс: частые слова («Господь», «сказал») исключаются стоп-списком.
- [Цитата верна текстуально, но вырвана из контекста] → кнопка «Показать контекст», оговорка на странице «О приложении», в промпте запрет на стихи, где слова принадлежат отрицательному персонажу (например, речи друзей Иова, слова змея), без явного указания на это в пояснении.
- [Модель пропускает оправдание вреда] → эвристический бэкстоп (D7). Ложные срабатывания допустимы: пользователь переформулирует.
- [Размер корпуса для клиентского поиска по ключевым словам] → загрузка только при шаге 2 fallback, gzip/brotli от Cloudflare, кеш браузера. Основной путь (LLM) грузит 1–3 книги.
- [Лицензия и качество исходного JSON] → проверки эталонов в скрипте сборки (D2). Источник фиксируется в README и на странице «О приложении».
- [Бесплатные лимиты Groq меняются] → переключение провайдера через `LLM_PROVIDER` без правки кода, как в Astro.
- [Лимиты Groq для gpt-oss-120b на бесплатном тарифе: 8000 токенов в минуту, 1000 запросов и ~200 тыс. токенов в сутки; с учётом второго прохода (D5a) один запрос ≈ 3,5–4 тыс. токенов] → ИИ обслуживает ~2 запроса в минуту и ~50–55 в сутки, остальное — упрощённый подбор (пользователь всегда получает ответ). Промпт сокращён (только сокращения книг). Если лимита мало — платный тариф Groq или другой провайдер.
- [Модель путает направленность стиха (Ис 5:11 «Горе тем…» как подтверждение допустимости вина) и пишет пояснение, не относящееся к тексту стиха (Притч 12:17 «кто говорит то, что знает…» с пояснением «стих хвалит молчание»)] → направленность нельзя проверить по корпусу; улучшается промптом по эталонному прогону (задача 7.2).

## Migration Plan

Новый проект, миграций нет. Деплой: создать GitHub-репозиторий `ibo-skazano` и Cloudflare Pages проект `ibo-skazano` с KV `RATE_LIMIT_KV`, задать секреты, выполнить `npm run build && wrangler pages deploy dist`. Откат — повторный деплой предыдущей сборки или переключение на прошлый деплой в панели Cloudflare. `git push` и первая публикация — только после подтверждения пользователя.
